ROLE
You are an expert systems engineer extending Visual DNA Studio with a fast, practical
“Component + Material Intelligence” pipeline.

Goals:
1) Detect likely UI components (button/knob/slider/card/panel/etc.) and their bounding boxes.
2) Infer material + layer topology (glass, metal, plastic, emissive, etc.) including texture + opacity cues.
3) Emit reusable representations as:
   - W3C DTCG 2025.10 tokens (canonical)
   - Namespaced extensions for material, texture, and interaction bindings (optional/ignorable)
4) Integrate into the existing pipeline architecture (add stages + endpoints; do not break existing flows).

Timing:
- Should be fast. Near-realtime is ideal, but “fast enough for iterative use” is acceptable.
- Must degrade gracefully when AI calls are slow or fail.

---

NON-NEGOTIABLES

- Must integrate with existing Python CV pipeline + Node/TS API.
- Must output W3C DTCG-compliant JSON for standard token types.
- Add extensions under a clear namespace (e.g. material.*, texture.*, components.*, interaction.*).
- Must be explainable and debuggable (store intermediate artifacts + metrics).
- Prefer deterministic CV and lightweight heuristics; AI is for semantic compression, not magic.

STEP 1 — COMPONENT DETECTION (FAST, PRACTICAL)

Create:
  python/components/detect.py

Implement a two-tier approach:

A) Deterministic CV proposals (default path)
- Preprocess: resize to max 1024 px on longest edge
- Edge map (Canny), morphology close/open
- Find contours + rectangles
- Filter by area, aspect ratio, solidity
- Cluster rectangles into likely component candidates
- Derive component “shape features”:
  - roundness, corner radius estimate
  - symmetry
  - gradient presence
  - icon/text presence (optional quick OCR later)

Output candidates:
[
  {
    "id": "c1",
    "bbox": [x, y, w, h],
    "shape": {"roundness": 0.78, "radiusHint": 12, "rectangularity": 0.92},
    "visual": {"hasText": false, "hasIcon": true, "dominantGradient": true}
  },
  ...
]

B) Optional AI classification (only if enabled / budget allows)
- Send downsampled image + candidate bboxes + shape features
- Model returns labels from a constrained ontology:
  ["button", "knob", "slider", "toggle", "card", "panel", "tab", "input", "badge", "unknown"]
- No prose, no new categories

If AI fails:
- Keep candidates as "unknown" but still usable.

STEP 2 — MATERIAL SIGNAL EXTRACTION (DETERMINISTIC)

Create:
  python/material/signals.py

Compute global + per-component material cues:
- translucency_score (0..1)
  - edge softness (Laplacian variance, edge falloff)
  - local contrast attenuation (compare inside bbox vs immediate outside ring)
- specular_density (0..1)
  - count of high-luma pixels with strong gradients
  - directionality of highlights (Hough line hints / oriented gradients)
- emission_score (0..1)
  - halo detection: bright pixels bleeding beyond shape boundary
  - saturation spikes near edges / internal cores
- depth_shadow_complexity
  - estimate shadow layers using shadow-like regions below/around components

Return:
{
  "global": {...},
  "perComponent": {"c1": {...}, ...}
}

---

STEP 3 — TEXTURE SIGNAL EXTRACTION (DETERMINISTIC)

Create:
  python/texture/signals.py

Extract texture cues (global + per-component) using light classic features:
- texture_grain (0..1)
  - high-frequency energy ratio (FFT band energy or Laplacian energy)
- microcontrast (0..1)
  - local contrast statistics (CLAHE delta proxy)
- anisotropy (0..1)
  - oriented gradient histogram concentration (brushed metal / fabric hints)
- noise_type_hint (categorical)
  - ["none", "film_grain", "dither", "speckle", "patterned"]
- pattern_period_hint (optional)
  - detect repeating patterns (autocorrelation peak)

Return compact values; keep it cheap.

STEP 6 — TOKEN + REPRESENTATION OUTPUT

Add three outputs:

A) DTCG Tokens (canonical)
- continue assembling existing tokens
- add any new standard tokens where possible:
  - opacity tokens as numbers
  - shadows as shadow composites if you already support them

B) Namespaced Extensions (optional/portable)
- components.*:
  components.c1.bbox, components.c1.type, components.c1.confidence
- material.*:
  material.type, material.finish, material.translucency, material.reflectivity, material.emission.*
- texture.*:
  texture.kind, texture.grain, texture.anisotropy, texture.scale
- interaction.*:
  interaction.bindings[] as objects with input/target/curve

Ensure these extensions do not break validators:
- keep them under a single extension namespace root or clear prefixes
- mark them as $type "object" where necessary

Example extension token pattern:
{
  "material.type": { "$value": "glass", "$type": "string" },
  "texture.grain": { "$value": 0.2, "$type": "number" },
  "components.c1": { "$value": { "bbox":[...], "type":"button", "confidence":0.74 }, "$type":"object" }
}
